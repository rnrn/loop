# Прогон мастер-класса по шагам

Что делать, что при этом происходит и что говорить группе.
Одна команда за раз. Не уходить вперёд до контрольной точки.

Условные обозначения: **Вы** — участник за ноутбуком, **Модератор** — ведущий.
Все команды выполняются в корне репозитория.

---

## Часть 0. Подготовка (до занятия)

| Шаг | Команда | Что должно быть |
| --- | --- | --- |
| 0.1 | `git clone <url> loop && cd loop` | Проект получен |
| 0.2 | `npm run bootstrap` | Node, зависимости, Chromium, самопроверка зелёные |
| 0.3 | `npm run preflight` | Порты свободны, чекпоинты 4/4, Chromium стартует |
| 0.4 | `npm run verify` | Материал согласован (проверка модератора, ~3 мин) |

`npm run bootstrap` не требует `npm install` — делает всё сам. Сам мастер-класс
зависимостей не имеет: `npm run dev` и `npm test` работают на голом Node.

**Модератор проверяет руками:** микрофон и разрешения в выбранном браузере,
coding agent установлен и авторизован, проектор показывает шрифт терминала.

---

## Часть 1. Story 1 — пройти цикл с готовым гейтом

Здесь спека и тесты готовы заранее. Участник учится **проходить** цикл.

### 1.1 Встать на старт

```
npm run checkpoint -- 00 --force
```

Рабочее дерево заменяется стартером: заглушки вместо реализации,
открыт только этап Story 1.

> **Говорим:** «Сегодня мы не просим ИИ сделать приложение целиком. Берём одну
> маленькую Story, сначала видим FAIL, потом разрешаем агенту минимальное
> изменение, и закрываем этап только после независимой проверки».

### 1.2 Посмотреть scope

```
npm run trace
```

Восемь критериев `S1-01…S1-08`. Story 2 и change request не показаны —
модератор их не открыл.

> **Говорим:** «Жёлтые пункты — S1-01 и S1-07 — не закроет ни один тест и ни
> один агент. Это ваши руки. Зелёный `npm test` не равен готовой Story».

Прочитать `stories/1-record-audio.md` и `SPEC.md`.

### 1.3 Увидеть FAIL

```
npm test
```

Ожидается: `tests 9, pass 0, fail 9`, жёлтый `FAIL`.

> **Говорим:** «Это доказательство незавершённости, привязанное к конкретным
> кодам. Дальше любое изменение оценивается не мнением, а тем, сдвинулись ли
> эти девять проверок». Красного нет намеренно: FAIL здесь — вход в цикл.

**Контрольная точка A:** у всех виден одинаковый FAIL 0/9.

### 1.4 Реализация

Промпт агенту (одинаковый для всех столов):

```
Реализуй только Story 1 из stories/1-record-audio.md.
Сначала прочитай AGENTS.md, SPEC.md, LOOP.md и существующие тесты.
```

Требования не перечисляем: они лежат в `SPEC.md`, `LOOP.md`, `AGENTS.md` и
самой Story. Это и есть разница между prompt engineering и context engineering.

**За чем следить:** какие файлы агент трогает (`tests/` — стоп),
не добавляет ли лишнего, счётчик тестов остался 9.

### 1.5 Автоматический гейт

```
npm test
```

Ожидается `9/9`.

**Проверить, а не поверить:**

```
diff -rq checkpoints/checkpoint-00-start voice-notes-workshop
```

Должны отличаться только `src/app.js`, `src/recording.js`,
`src/recordings-store.js`.

**Контрольная точка B:** у всех 9/9, тесты не тронуты.

### 1.6 Ручной сценарий

```
npm run dev
```

Открыть http://localhost:5173/ и выполнить общий сценарий — фразы одинаковые
у всех столов:

1. «Подготовить микрофон», выдать разрешение → кнопка READY. **S1-01**
2. Зажать, сказать «Первая тестовая голосовая заметка», отпустить.
3. Зажать, сказать «Вторая запись должна находиться сверху», отпустить.
4. Зажать, отвести курсор **за пределы кнопки**, отпустить там. **S1-04**

Проверить: две карточки, новая сверху (**S1-06, S1-07**), обе играют
(**S1-05**), кнопка вернулась в READY (**S1-02**), консоль чистая (**S1-08**).

> **Говорим:** «Тесты работали с подделкой. Сейчас впервые участвуют настоящий
> MediaRecorder, настоящее разрешение и настоящий Blob».

**Контрольная точка C:** у всех две реальные записи.

### 1.7 Evidence

Записать в `progress.md` команду, результат и ручные проверки.
Статус Story → `done`.

> **Говорим:** «Story закрыта не потому, что агент написал "готово", а потому
> что есть свежий PASS и записанное доказательство».

## Часть 2. Story 2 — сделать этап с нуля

Здесь **ничего не заготовлено**: ни спеки, ни тестов. Участник учится
**создавать** гейт. Это ответ на вопрос «откуда берутся тесты».

Заготовлены только заглушка `src/speech-recognition.js` (архитектурный шов из
SPEC §3.5) и `?mock-stt=1` — чтобы столы не разошлись по разным приложениям.

### 2.1 Открыть этап

```
npm run story:next
```

### 2.2 Упереться в пустоту

```
npm test
```

Ожидается:

```
СПЕКИ НЕТ — этап «Story 2 — расшифровка» ещё не готов к проверке.
  → 1. stories/2-add-transcription.md — спека: критерии с кодами в таблице
  → 2. tests/speech-recognition.test.js — гейт, отдельным проходом
    3. npm run gate — гейт обязан быть КРАСНЫМ
    4. человек читает тесты и замораживает их
    5. только теперь реализация
```

Это не подсказка, а стена: `exit=2`, этап пройти нельзя.

> **Говорим:** «Story 1 вы прошли с готовыми тестами. Кто их написал? Я, до
> занятия. На вашей работе их никто не напишет — сейчас пишем сами».

### 2.3 Обсудить продуктовые фичи — ДО агента

Разговор группой, 5 минут. Что вообще должна делать расшифровка:

- Что если браузер не умеет распознавать речь? (fallback, а не поломка)
- Что важнее — аудио или текст? (аудио; STT это progressive enhancement)
- Что если распознавание пришло, когда пользователь уже пишет следующую заметку?
- Что если распознавание упало с ошибкой? (аудио остаётся)

> **Говорим:** «Заметьте, мы решаем продуктовые вопросы до того, как что-то
> написано. Если отдать их агенту, он ответит за вас — и ответит правдоподобно».

### 2.4 Написать спеку

Промпт:

```
Напиши stories/2-add-transcription.md по образцу stories/1-record-audio.md.

Тема: расшифровка речи как progressive enhancement.
Прочитай SPEC.md и AGENTS.md.

Обязательно таблица acceptance criteria с кодами S2-01, S2-02, ...
в формате: Код | Критерий | Чем проверяется
В третьей колонке: `npm test` для того, что проверяется автоматически,
«ручной сценарий» для того, что проверяет человек в браузере.

Учти решения группы:
- аудио сохраняется независимо от результата STT;
- при отсутствии поддержки — понятный fallback;
- результат может прийти позже создания карточки;
- ошибка STT не удаляет аудио.

Тесты и реализацию не трогай. Только файл спеки.
```

**Прочитать глазами.** Спека — то, по чему потом судят результат;
если она врёт, врать будет всё остальное.

```
npm run trace
```

Все критерии `S2-xx` показаны как «нет теста». Так и должно быть.

### 2.5 Написать гейт — отдельным проходом

```
Напиши тесты для Story 2 по acceptance criteria из stories/2-add-transcription.md.
Прочитай AGENTS.md, SPEC.md, LOOP.md.

Только tests/speech-recognition.test.js. Реализацию не трогай:
src/speech-recognition.js и src/recordings-store.js остаются как есть.

Имя каждого теста начинай с кода критерия: S2-01, S2-02, ...
Критерии с пометкой «ручной сценарий» тестами не покрывай.

После написания запусти npm run gate. Тесты обязаны падать.
```

> **Говорим:** «Отдельный проход обязателен. Если писать тест и код за один
> заход, проверка подстроится под то, что получилось».

### 2.6 Доказать гейт

```
npm run gate
```

Три возможных исхода:

| Вывод | Значение | Что делать |
| --- | --- | --- |
| `ГЕЙТ ЗАФИКСИРОВАН` | тесты падают до реализации | дальше |
| `ГЕЙТ НЕ ДОКАЗАН` | всё зелёное до кода | тест подогнан или не проверяет ничего |
| `ГЕЙТА НЕТ` / `СПЕКИ НЕТ` | файла нет | вернуться на 2.4 или 2.5 |

> **Говорим:** «Тест, который ни разу не падал, ничего не доказывает».

### 2.7 Прочитать и заморозить

Прочитать тесты глазами. Сверить с `npm run trace`: коды на месте, ручные
критерии не подменены автоматическими. С этого момента тесты read-only.

**Контрольная точка D:** у всех красный гейт, принятый человеком.

### 2.8 Реализация

```
Реализуй только Story 2 из stories/2-add-transcription.md.
Сначала прочитай AGENTS.md, SPEC.md, LOOP.md и тесты этапа.
Тесты не изменяй.
```

### 2.9 Проверка

```
npm test
```

Зелёными должны быть и `S1-xx`, и `S2-xx`: открытый этап всегда тянет за собой
предыдущий, поэтому регрессия проверяется сама собой.

Ручной сценарий: записать «Сегодня мы проверяем расшифровку голосовой заметки».
Допустимы обе ветки — текст или «Расшифровка недоступна». Если STT недоступен,
`http://localhost:5173/?mock-stt=1`.

**Контрольная точка E:** текст или fallback, полный набор зелёный.

### 2.10 Evidence

`progress.md`, статус Story → `done`.

## Часть 3. Change request — опционально

Только при наличии времени. Первым режется при отставании.

```
npm run story:next
npm test                  # снова FAIL: система стала незавершённой
```

Промпт — по `change-requests/1-collapse-long-transcripts.md`.
Гейт здесь заготовлен: цель этапа — показать повторный цикл при изменении
требований, а не ещё раз писать тесты.

## Часть 4. Ретроспектива

Вопросы группе:

- Где в этом цикле была **цель**? (Story и acceptance criteria)
- Где **память**? (SPEC, LOOP, тесты, progress.md — вне чата)
- Где **проверка**? (npm test + ручной сценарий, два разных яруса)
- Где **правило остановки**? (PASS, BLOCKED, RETRY_LIMIT, TIMEBOX_EXPIRED)
- Чем Story 2 отличалась от Story 1? (гейт создавали, а не получали)

> **Итог:** «Prompt engineering задаёт инструкцию. Context engineering даёт
> правильные данные. Loop engineering организует повторяемое движение от
> незавершённой Story к проверенному результату».

## Если что-то пошло не так

| Ситуация | Действие |
| --- | --- |
| Микрофон запрещён политикой | `?mock-stt=1`, либо checkpoint |
| Агент полез в `tests/` | Остановить, `git checkout -- voice-notes-workshop/tests/` |
| Агент реализовал всё сразу | `npm run checkpoint -- 00 --force`, повторить Story |
| Три попытки не помогли | RETRY_LIMIT: зафиксировать причину, перейти на checkpoint |
| Группа отстаёт | Убрать change request; Story 2 показать через `checkpoint -- 02` |
| Не успели написать гейт | `npm run checkpoint -- 02 --force` — там эталонные тесты |

Откат не скрывает ошибку, а сохраняет общий темп: участник фиксирует проблему
как BLOCKED или RETRY_LIMIT и продолжает следующий цикл вместе с группой.

Сохранить своё состояние перед откатом: `npm run checkpoint -- save моё-имя`.

| --- | --- | --- |
| Подготовка, старт, FAIL | 15 мин | 10 мин |

это и есть содержание loop engineering.
