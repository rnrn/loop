# Loop Engineering — браузерный диктофон

Мастер-класс: полный инженерный цикл Story → FAIL → реализация → проверка →
исправление → PASS на примере браузерного диктофона с расшифровкой.

Проект восстановлен из методички мастер-класса и прогнан по сценарию целиком.
Сама методичка в репозиторий не входит — она у модератора.

## Быстрый старт

```bash
git clone <url> loop_denmo
cd loop_denmo
npm run bootstrap
```

`bootstrap` не требует предварительного `npm install` — он делает всё сам:
проверяет Node.js, целостность структуры §3.6 и наличие чекпоинтов §8.2,
ставит зависимости, скачивает Chromium и запускает самопроверку
(рабочее дерево обязано быть зелёным, `checkpoint-00-start` — красным).

```bash
npm run bootstrap -- --skip-browsers   # без Chromium (~150 МБ)
npm run bootstrap -- --quick           # без финальной самопроверки
```

**Сам мастер-класс зависимостей не имеет.** `npm run dev` и `npm test` работают
на голом Node (`node:http`, `node:test`), как требует §3.5. npm-пакеты нужны
только для автопрогона ручного сценария в браузере — участникам они не нужны.
Если интернета нет, `bootstrap` доложит об этом и занятие всё равно можно вести.

## Команды

| Команда | Что делает |
| --- | --- |
| `npm run bootstrap` | Развернуть проект после клонирования |
| `npm run preflight` | Проверка окружения перед занятием (§8.1): Node, порты, чекпоинты, Chromium + чек-лист ручных пунктов |
| `npm run dev` | http://localhost:5173/ — и `/?mock-stt=1` для mock-режима §7.6 |
| `npm test` | Тесты **активного этапа** и всего пройденного до него |
| `npm run test:all` | Весь набор целиком |
| `npm run trace` | Карта покрытия: какой критерий закрыт тестом, какой — ручным сценарием |
| `npm run story` | Где мы сейчас: какие этапы открыты, какой активен |
| `npm run story:next` | Открыть следующий этап (действие модератора) |
| `npm run story:reset` | Вернуться к Story 1 |
| `npm run scenario:all` | Прогон ручного сценария в браузере, все 4 ветки |
| `npm run scenario:story1` \| `:fallback` \| `:story2` \| `:cr` | Одна ветка сценария |
| `npm run verify` | Полная регрессия: дерево + все чекпоинты + все ветки сценария |
| `npm run checkpoint -- list` | Список чекпоинтов |
| `npm run checkpoint -- 01` | Показать, что даст откат (ничего не меняет) |
| `npm run checkpoint -- 01 --force` | Выполнить откат |
| `npm run checkpoint -- save <имя>` | Снимок текущего состояния |

Откат без `--force` только показывает намерение — он затирает работу участника,
поэтому подтверждается явно.

## Одна Story за раз

Модератор открывает только текущую Story (§2.3), и `npm test` это уважает:
тесты будущих этапов лежат в репозитории с самого начала, но не запускаются.
Участник видит FAIL ровно по своей задаче, а не по всему курсу.

```
npm test            →  Активный этап: Story 1 — запись аудио
                       tests 9, pass 0, fail 9      ← стартовый FAIL
                       Скрыто этапов впереди: 2

# Story 1 реализована
npm test            →  tests 9, pass 9, fail 0

npm run story:next  →  Открыт этап: Story 2 — расшифровка
npm test            →  tests 20, pass 9, fail 11     ← снова незавершённое состояние,
                                                       Story 1 при этом держится
```

Регрессия проверяется сама собой: открытый этап всегда тянет за собой все
предыдущие. `npm run test:all` показывает полный набор в любой момент —
он нужен модератору, а не участнику.

Состояние хранится в `voice-notes-workshop/workshop.state.json`,
список этапов — в `voice-notes-workshop/tools/stages.mjs`.

## Коды acceptance criteria

У каждого критерия есть код: `S1-01…S1-08`, `S2-01…S2-07`, `CR-01…CR-07`.
Одни и те же коды стоят в Story, в именах тестов и в пунктах ручного
сценария, поэтому порядок появления функциональности виден везде одинаково,
а тесты сортируются по возрастанию кода:

```
S1-02  подготовка микрофона переводит NEEDS_PERMISSION → READY
S1-03  pointerdown не начинает запись без разрешения
S1-04  повторный stop не вызывает MediaRecorder.stop() ...
```

`npm run trace` показывает карту покрытия и сторожит рассинхрон: критерий
с пометкой «`npm test`», но без теста, и тест с кодом, которого нет ни в
одной Story, помечаются как проблема. Проверка входит в `npm run verify`.

Из 22 критериев 13 закрыты автоматически, 9 — только ручным сценарием:
браузерную интеграцию unit-тесты не заменяют (§7.1).

## Структура

| Путь | Что это |
| --- | --- |
| `voice-notes-workshop/` | Рабочий репозиторий (сейчас — состояние после change request) |
| `checkpoints/checkpoint-00-start` | Стартовое состояние участника: **9 тестов красные** (только Story 1) |

| `checkpoints/checkpoint-02-stt` | После Story 2 |
| `checkpoints/checkpoint-03-collapse` | После change request |

Структура `voice-notes-workshop/` соответствует §3.6; содержимое `SPEC.md`,
`LOOP.md`, `AGENTS.md`, `stories/`, `change-requests/`, `progress.md` взято
из приложений A–G.

## Прогон сценария: результаты

| Этап | Автоматически | Ручной сценарий в браузере |
| --- | --- | --- |
| Стартовый FAIL | **0 pass / 9 fail** — только Story 1 | — |
| Story 1 | `npm test` → **9/9** | **8/8** |
| Story 2 | `npm test` → **20/20** (с регрессией Story 1) | **10/10** ×2 ветки |
| Change request | `npm test` → **24/24** (с регрессией обеих Stories) | **19/19** |

`npm run verify` → **9/9**.

Ручной ярус — не эмуляция: настоящий Chromium с
`--use-fake-device-for-media-stream`, реальные pointer-события, реальный
`MediaRecorder`, реальное воспроизведение (`currentTime > 0`). Микрофон заменён
fake-устройством, поэтому фразы из §6.4 проверяются как две записи, а не как
распознанный текст.

## Что цикл поймал по-настоящему

На ветке `?mock-stt=1` карточка застревала на статусе «Расшифровка…».
Первопричина: mock отдавал результат **раньше**, чем создавалась аудиокарточка,
и обновление по `id` не находило запись — текст терялся. Документ описывает
только обратный случай («STT может завершиться позже создания карточки»),
симметричный не покрыт. Починено буфером `pendingPatches` в `src/app.js`;
ручная проверка ужесточена, чтобы pending-подпись больше не засчитывалась
как результат. Тесты не ослаблялись.

## Расхождения с документом

1. **Область `npm test` привязана к активному этапу** (`tools/`,
   `workshop.state.json`). §3.6 кладёт в стартер оба тест-файла, но тогда на
   этапе 2 участник видел бы 24 красных теста вместо «теста Story 1 ожидаемо
   красного». Документ на этапе 7 говорит «npm test», а на этапе 12 —
   «**полный** npm test»: это и есть разделение на активную область и полный
   набор. Реализовано без правки самих тестов — меняется только то, какие
   файлы запускаются.
2. **`tests/collapse-transcript.test.js`** отсутствует в §3.6. Лежит в стартере
   с самого начала, но этап change request закрыт, поэтому на стартер он не
   влияет — раздавать файл руками не нужно.
3. **Dev-сервер.** §7.6 упоминает порт 5173 (vite), но ставить vite ради
   статики нельзя без `npm install`; используется свой `dev-server.js` на 5173.
4. **Регрессия раннего STT** покрыта ручным ярусом, а не unit-тестом:
   по §7.1 браузерная интеграция проверяется ручным сценарием.
