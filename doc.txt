Как пользоваться документом
Документ объединяет методическую логику, продуктовую спецификацию, подробный сценарий по минутам, готовые промпты, тесты и файлы для starter repository. Основная часть нужна модератору для проведения занятия; приложения можно копировать в проект почти без изменений.

Ключевое решение для повторяемости
Эпик, истории, тесты и starter repository готовятся заранее. Участники не генерируют собственный план: они синхронно выполняют одну и ту же Story, используют одинаковый промпт, произносят одинаковые тестовые фразы и останавливаются в общих контрольных точках.

Что именно участники должны понять и построить

1.1. Учебная цель
Участники не просто получают страницу, сгенерированную ИИ. Они видят управляемую последовательность, в которой работа представлена отдельной Story, результат проверяется автоматическими и ручными критериями, ошибка становится входом следующей итерации, а состояние сохраняется вне чата.

Формула занятия
Не «попросить ИИ сделать приложение», а провести одну работу через повторяемый цикл: сформулировать → проверить незавершённость → реализовать → получить доказательство → зафиксировать результат → перейти дальше.

1.2. Почему выбран диктофон
Результат понятен без специальной подготовки: зажал кнопку, произнёс фразу, отпустил, увидел запись.
Есть реальная работа с браузерным API, поэтому участники видят отличие unit-теста от ручной интеграционной проверки.
Функциональность легко разделяется на две независимые Stories: аудио и расшифровка.
Есть естественный fallback: отсутствие STT не ломает основную ценность — аудиозапись.
Можно добавить маленькое изменение требований и показать повторный цикл без переписывания проекта.
1.3. Зафиксированный scope
Категория
Содержание
Обязательно
Подготовка микрофона; запись при удержании; остановка при отпускании; новая карточка сверху; воспроизведение; несколько записей; понятная ошибка.
Обязательно с fallback
Расшифровка через браузерный STT при наличии поддержки; иначе статус «Расшифровка недоступна». Аудио сохраняется независимо от STT.
Только при наличии времени
Ограничение расшифровки четырьмя строками; просмотр полного текста по клику или кнопке; aria-expanded.
Не входит
Backend, база данных, аккаунты, загрузка на сервер, сохранение после перезагрузки, удаление, скачивание, waveform, сложный дизайн, аналитика.

1.4. Что получает участник
Рабочую локальную страницу с диктофоном.
Две завершённые Stories с доказательствами PASS.
Понимание роли SPEC.md, Story, тестов, ручного сценария и progress.md.
Опыт корректной деградации функции, зависящей от браузера или внешнего сервиса.
Шаблон цикла, который можно перенести на собственную специальность.

2.2. Из чего состоит управляемый loop
Элемент
Как реализован на мастер-классе
Trigger
Есть Story со статусом todo или in_progress.
Goal
Выполнить её acceptance criteria, не расширяя scope.
Action
Внести минимальное изменение в код.
Verification
Запустить автоматические тесты и общий ручной сценарий.
Feedback
Использовать конкретный вывод FAIL как вход следующей попытки.
Memory
SPEC.md, Story, tests и progress.md сохраняют состояние вне чата.
Stop rule
PASS, BLOCKED, RETRY_LIMIT или TIMEBOX_EXPIRED.

2.3. Роли
Роль
Ответственность
Модератор
Управляет темпом, открывает только текущую Story, выдаёт фиксированный промпт, объявляет точки проверки и change request.
Участник
Повторяет действия, наблюдает за агентом, не принимает лишний scope, запускает проверки и фиксирует evidence.
ИИ-агент
Читает контекст проекта, изменяет код, запускает тесты, исправляет первопричину и останавливается в пределах Story.
Тесты и браузер
Выступают независимым quality gate: автоматическая логика плюс реальное взаимодействие с микрофоном.

2.4. Источники истины
SPEC.md — цель, границы, состояния и неизменяемые правила.
Story — маленькая единица результата с Given/When/Then.
tests — детерминированная проверка логики.
Общий ручной сценарий — проверка браузерной интеграции.
progress.md — доказательства и состояние между итерациями.
2.5. Правила остановки
Состояние
Когда применяется
DONE
Все критерии Story выполнены, свежий npm test проходит, ручной сценарий записан в progress.md.
BLOCKED
Нужно решение или доступ, которого нет у участника: например, корпоративная политика блокирует микрофон.
RETRY_LIMIT
Три попытки агента не устранили ошибку; участник переходит на резервный checkpoint.
TIMEBOX_EXPIRED
Истёк лимит этапа; модератор переводит группу на готовую ветку и продолжает обучение.


Почему нужен лимит попыток
Без RETRY_LIMIT и TIMEBOX_EXPIRED одна ошибка может поглотить занятие. Цель мастер-класса — увидеть цикл целиком, а не любой ценой отладить уникальную проблему одного ноутбука.

3
Спецификация приложения-диктофона
Единое поведение, которое реализуют все участники

3.1. Пользовательский сценарий
Пользователь нажимает «Подготовить микрофон» и выдаёт разрешение.
После подготовки видит кнопку «Зажмите, чтобы записать».
На pointerdown начинается запись, кнопка показывает активное состояние.
На pointerup или pointercancel запись останавливается.
Создаётся аудиокарточка с плеером; новая карточка добавляется наверх списка.
Если STT поддерживается, к карточке добавляется итоговая расшифровка.
Если STT недоступно или завершилось ошибкой, аудио остаётся, а карточка показывает fallback.
3.2. Почему разрешение запрашивается отдельно
Первый доступ к микрофону может открыть системный диалог. Если одновременно пытаться использовать первый pointerdown как начало записи, участник способен отпустить кнопку до выдачи разрешения, и разные ноутбуки попадут в разные состояния. Поэтому подготовка потока — отдельный нулевой шаг.
3.3. Модель состояний интерфейса
Состояние
Текст интерфейса
Правило
NEEDS_PERMISSION
«Подготовить микрофон»
Ожидается явное действие пользователя.
READY
«Зажмите, чтобы записать»
MediaStream получен; можно начать запись.
RECORDING
«Идёт запись — отпустите»
MediaRecorder активен; повторный start запрещён.
PROCESSING
«Сохраняем запись…»
Собирается Blob и создаётся карточка.
ERROR
Понятное сообщение рядом с кнопкой
Можно повторить подготовку или вернуться в READY.

Схема переходов
NEEDS_PERMISSION
        ↓ разрешение получено
      READY
        ↓ pointerdown
    RECORDING
        ↓ pointerup / pointercancel
    PROCESSING
        ↓ Blob создан
      READY

любое состояние → ERROR → повтор разрешения или READY

3.4. Модель одной записи
Рекомендуемая структура данных
{
  id: "уникальный-id",
  audioUrl: "blob:...",
  createdAt: 1234567890,
  transcript: "",
  transcriptStatus: "pending", // ready | unavailable | error
  expanded: false
}

Идентификатор создаётся в момент начала записи. Тогда поздно пришедший результат STT может обновить именно ту карточку, к которой относится, даже если пользователь уже начал следующую запись.
3.5. Технические ограничения
Область
Решение
Интерфейс
HTML, CSS, JavaScript без UI-фреймворка.
Сервер
Не требуется; приложение работает локально.
Запись
MediaDevices.getUserMedia + MediaRecorder.
Удержание
Pointer Events: pointerdown, pointerup, pointercancel; желательно pointer capture.
Расшифровка
SpeechRecognition или webkitSpeechRecognition, язык ru-RU; это progressive enhancement.
Тесты
Встроенный node:test или уже подготовленный runner; внешние зависимости минимальны.
Данные
Не использовать реальные рабочие, персональные или конфиденциальные сведения.

4
Epic, Stories и изменение требований
Маленький scope, который можно завершить синхронно

4.1. Epic

Epic: голосовые заметки
Пользователь должен быстро записать несколько голосовых заметок в браузере, сразу воспроизвести их и, при наличии поддержки, увидеть расшифровку. Новая запись всегда находится в начале списка.

4.2. Story 1 — запись аудио
Как пользователь, я хочу удерживать кнопку для записи короткой голосовой заметки и после отпускания видеть её сверху списка, чтобы сразу воспроизвести результат.
ACCEPTANCE CRITERIA
Доступ к микрофону запрашивается отдельным действием.
pointerdown начинает запись только из состояния READY.
pointerup и pointercancel безопасно останавливают активную запись.
После остановки создаётся Blob и карточка с audio controls.
Каждая новая карточка добавляется в начало списка.
Можно последовательно создать не менее двух записей.
Отказ в доступе или отсутствие микрофона показывают понятную ошибку.
Given / When / Then
Scenario: записаны две заметки
  Given микрофон подготовлен
  When пользователь записывает первую и затем вторую заметку
  Then в списке есть две карточки
  And вторая запись находится выше первой
  And обе записи можно воспроизвести

Scenario: отпускание вне кнопки
  Given запись началась на pointerdown
  When pointerup или pointercancel происходит вне кнопки
  Then активная запись завершается ровно один раз

Scenario: микрофон недоступен
  Given браузер отклонил getUserMedia
  When пользователь пытается подготовить микрофон
  Then интерфейс показывает понятное сообщение
  And приложение не падает

4.3. Story 2 — расшифровка как progressive enhancement
Как пользователь, я хочу видеть текст рядом с аудиозаписью, когда браузер умеет распознавать речь, и понятный fallback, когда распознавание недоступно.
ACCEPTANCE CRITERIA
Поддержка определяется через SpeechRecognition или webkitSpeechRecognition.
При наличии конструктора используется язык ru-RU.
Собираются финальные результаты распознавания.
Результат связывается с id соответствующей записи.
STT может завершиться позже создания аудиокарточки.
Отсутствие или ошибка STT не удаляют и не блокируют аудио.
При неподдерживаемом STT отображается «Расшифровка недоступна».
Given / When / Then
Scenario: STT поддерживается
  Given браузер предоставляет SpeechRecognition
  When пользователь завершает запись
  Then аудиокарточка появляется независимо от STT
  And итоговый текст добавляется в ту же карточку по id

Scenario: STT не поддерживается
  Given оба конструктора SpeechRecognition отсутствуют
  When пользователь завершает запись
  Then аудио доступно для воспроизведения
  And карточка показывает «Расшифровка недоступна»

Scenario: STT завершилось ошибкой
  Given аудиозапись создана
  When распознавание сообщает ошибку
  Then аудио остаётся в списке
  And transcriptStatus становится error

4.4. Change request — длинные расшифровки

Объявляется только при наличии времени
Длинная расшифровка занимает максимум четыре строки. Полный текст раскрывается по клику на текст или отдельную кнопку. Аудиоплеер и метаданные всегда остаются видимыми.

Ограничивать только текстовый блок, а не всю карточку.
Клик по audio controls не должен переключать раскрытие.
Состояние expanded хранится для конкретной записи.
Интерактивный элемент получает aria-expanded.
Все тесты Story 1 и Story 2 продолжают проходить.
4.5. Почему всего две обязательные Stories
Цель занятия — пройти цикл целиком. Большой dependency-граф, пять параллельных агентов или десяток пользовательских историй повышают вероятность того, что группа разойдётся по разным ошибкам и не увидит завершение. Две Stories дают достаточно материала для обучения: создание основной функции, интеграция нестабильной зависимости и проверка отсутствия регрессии.


5
Полный сценарий мастер-класса
Формат: что делает модератор — что делают участники — результат этапа

Базовый тайминг рассчитан на 75–85 минут. Этап 14 выполняется только при наличии времени. В каждом этапе модератор сначала показывает действие, затем участники повторяют его, после чего группа фиксирует общий результат.
Время и этап
Что делает модератор
Что делают участники
Результат этапа
0–5
1. Постановка задачи
Показывает готовый результат: записывает две заметки, демонстрирует, что новая находится сверху, а расшифровка является дополнением. Показывает схему Story → FAIL → реализация → PASS.
Смотрят демонстрацию. Не запускают агента и не пишут код.
Все одинаково понимают продукт и учебную цель.
5–10
2. Запуск starter repository
Просит открыть подготовленный проект. Показывает npm run dev и npm test.
Запускают сервер, открывают страницу и выполняют тесты.
У всех одинаковая стартовая страница; тест Story 1 ожидаемо красный.
10–15
3. Preflight микрофона
Просит нажать «Подготовить микрофон». Помогает с разрешениями и выбором устройства.
Выдают разрешение и проверяют переход кнопки в READY.
Технические проблемы найдены до основной разработки.
15–20
4. Чтение SPEC и Story 1
Открывает SPEC.md и 1-record-audio.md. Проговаривает обязательное и non-goals.
Читают те же файлы, сверяют acceptance criteria.
У всех одинаковый scope; лишние функции запрещены.
20–25
5. Первый запуск loop
Снова запускает тесты, показывает конкретный FAIL и выдаёт фиксированный промпт.
Повторяют npm test, копируют промпт агенту.
Цикл стартует из явно незавершённого состояния.
25–37
6. Реализация записи
Работает синхронно с группой. Подсвечивает pointer events, MediaRecorder, chunks, Blob, object URL и prepend.
Наблюдают за diff, отклоняют лишний scope, при необходимости возвращают агента к Story.
Кнопка начинает и завершает запись; создаётся карточка.
37–42
7. Автоматическая проверка Story 1
Останавливает реализацию и просит запустить npm test. При FAIL демонстрирует: прочитать ошибку → исправить причину → повторить.
Запускают тесты, передают агенту вывод ошибки, не ослабляют тесты.
Story 1 получает автоматический PASS.
42–50

7
Проверки, тесты и Definition of Done
Как доказать работоспособность, не тестируя реальный микрофон в unit-тестах

7.1. Разделение автоматических и ручных проверок
Настоящий микрофон и браузерный STT зависят от устройства, разрешений и окружения. Поэтому unit-тесты проверяют детерминированную логику, а единый ручной сценарий — интеграцию с браузером. Ни одна из частей не заменяет другую.
7.2. Минимальные автоматические тесты Story 1
prependRecording(newRecording, existing) возвращает массив, где новая запись находится первой.
Повторный вызов stop не вызывает MediaRecorder.stop(), если recorder уже inactive.
Состояние корректно возвращается из PROCESSING в READY после создания записи.
Ошибка подготовки микрофона переводит интерфейс в ERROR и не приводит к необработанному исключению.
7.3. Минимальные автоматические тесты Story 2
Наличие window.SpeechRecognition определяется как supported.
Наличие только window.webkitSpeechRecognition также определяется как supported.
Отсутствие обоих конструкторов возвращает unavailable.
STT error не удаляет запись и меняет только transcriptStatus.
Поздний результат обновляет запись по id, а не «последнюю карточку вообще».
7.4. Тест change request
toggleExpanded(id) меняет expanded только у указанной записи.
По умолчанию expanded равен false.
Существующие тесты записи и STT продолжают проходить.
7.5. Полный ручной чек

7.6. Режим mock-STT для повторяемости
Реальное распознавание может быть недоступно даже при одинаковых браузерах. В starter repository полезно предусмотреть учебный режим, например параметр ?mock-stt=1. В нём адаптер возвращает фиксированный текст, но приложение использует тот же интерфейс и тот же путь обновления записи.
http://localhost:5173/?mock-stt=1

Ожидаемый текст:
«Сегодня мы проверяем расшифровку голосовой заметки».


Правило использования mock
Сначала участник пробует реальный STT. Если результата нет или политика браузера блокирует функцию, модератор переводит его на mock, не меняя Story и критерии проверки.

7.7. Definition of Done всего мастер-класса
[PASS] Микрофон подготовлен либо корректно обработана недоступность.
[PASS] Удержание запускает запись, отпускание завершает её.
[PASS] После остановки создаётся воспроизводимая аудиокарточка.
[PASS] Новая запись появляется сверху.
[PASS] Созданы и воспроизводятся не менее двух записей.
[PASS] STT показывает текст или согласованный fallback.
[PASS] Полный npm test проходит.
[PASS] В консоли нет необработанных ошибок.
[PASS] progress.md содержит автоматические и ручные доказательства.

Приложение A. SPEC.md
# Voice Notes Workshop — Specification

## Goal
Пользователь удерживает кнопку, записывает короткую голосовую заметку
и сразу получает новую запись в начале списка для воспроизведения.
Если браузер поддерживает распознавание речи, карточка также получает
расшифровку.

## User flow
1. Нажать «Подготовить микрофон».
2. Выдать разрешение.
3. Удерживать кнопку для записи.
4. Отпустить для завершения.
5. Увидеть новую карточку сверху списка.
6. Воспроизвести аудио.
7. Увидеть текст или fallback STT.

## Required behavior
- Отдельный preflight микрофона.
- pointerdown начинает запись только из READY.
- pointerup и pointercancel завершают активную запись.
- Новая запись добавляется в начало списка.
- Можно создать несколько записей.
- Аудио является основным результатом.
- STT является progressive enhancement.
- Ошибка STT не удаляет аудио.

## States
NEEDS_PERMISSION, READY, RECORDING, PROCESSING, ERROR.

## Constraints
- HTML/CSS/JavaScript.
- Без backend и базы данных.
- Без сохранения после перезагрузки.
- Без загрузки реальных рабочих или персональных данных.
- Логика должна тестироваться через npm test.

## Non-goals
Удаление, скачивание, waveform, аккаунты, аналитика,
облачное хранилище, сложный дизайн.

## Success
Story считается завершённой только после свежего npm test,
общего ручного сценария и записи evidence в progress.md.

Приложение B. LOOP.md
# Development loop

Работай только с одной текущей Story.

1. Прочитай SPEC.md, текущую Story, тесты и progress.md.
2. Запусти npm test и зафиксируй незавершённое состояние.
3. Внеси минимальное изменение для acceptance criteria.
4. Не реализуй будущие Stories и non-goals.
5. Запусти npm test.
6. При FAIL:
   - прочитай конкретную ошибку;
   - запиши первопричину;
   - исправь её;
   - повтори проверку.
7. При PASS:
   - сравни реализацию со всеми criteria;
   - выполни ручной сценарий;
   - запиши evidence в progress.md;
   - пометь Story как done.
8. Не переходи к следующей Story без команды модератора.

Terminal states:
- DONE — Story проверена и evidence записан.
- BLOCKED — отсутствует необходимый доступ или решение.
- RETRY_LIMIT — три попытки не устранили ошибку.
- TIMEBOX_EXPIRED — завершён лимит этапа.

Запрещено:
- изменять или ослаблять тесты ради PASS;
- объявлять DONE без свежей проверки;
- расширять scope.

## New requirement
Длинная расшифровка по умолчанию занимает максимум четыре строки.
Пользователь может раскрыть и снова свернуть полный текст.

## Acceptance criteria
- Ограничивается только блок текста.
- Audio controls и метаданные всегда видимы.
- Переключение выполняется кликом по тексту или отдельной кнопке.
- Клик по audio не меняет expanded.
- Состояние хранится для конкретной записи.
- Интерактивный элемент имеет aria-expanded.
- Все существующие тесты продолжают проходить.

## Non-goals
Редизайн карточки, анимации, удаление и скачивание.

Приложение G. Минимальный AGENTS.md
# Agent instructions

- Read SPEC.md and LOOP.md before editing.
- Work on only the file named by the user.
- Prefer minimal changes.
- Do not implement future stories.
- Do not change tests unless the user explicitly requests it.
- Run npm test after changes.
- On failure, explain the root cause and retry.
- Stop after PASS or after three failed attempts.
- Record evidence in progress.md only after verification.

Приложение H. Финальная памятка модератора
Момент
Действие
До начала
Проект проверен; зависимости установлены; агент авторизован; микрофон и браузер протестированы; checkpoints и mock готовы.
Перед Story
Показать scope, acceptance criteria и ожидаемый FAIL.
Во время реализации
Не допускать лишних функций и изменения тестов.
После реализации
Сначала npm test, затем единый ручной сценарий.
Перед переходом
Записать evidence и дождаться общей контрольной точки.
При проблеме
Не превышать три попытки; использовать checkpoint и продолжить обучение.
В финале
Спросить: где цель, память, проверка и правило остановки?


Итоговая формула
Prompt engineering задаёт инструкцию. Context engineering даёт правильные данные. Harness engineering предоставляет среду и инструменты. Loop engineering организует повторяемое движение от незавершённой Story к проверенному результату.
